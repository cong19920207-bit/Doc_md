# 工作流程 · 文档工作台

> 讲解 / 方法，不是合同。改 Hayyo 规则仍改各功能 `prd/design/<功能>/PRD.md`。  
> 范围：本仓库约 2026-08 至 2026-09 已核对的主线。不含 V1.5.0 Word 专章、不含后台皮专章、不含其它产品仓库。  
> 证据来自仓库现行文档与同期对话。未写入文档的口头口径不编。

## 事情概述

这一个月做成的，不是「又写了一批 PRD」，而是把 **发版增量 Word** 变成 **可改、可读、可检索、可问答** 的分层文档。后一层都在修前一层留下的「人读不了 / 机器切不准」。

```text
Word / Excel              Aold_D/                 归档，不默认读
        ↓ 抽取（保真、按功能切开）
功能 PRD.md               prd/design/<id>/        现行唯一权威
        ↓ 解读叠覆盖 + RQ 拍板
brief/current.md          同目录 brief/           派生阅读层（给人读 + 给切块）
        ↓ 只切 <!-- chunk:default -->
向量 / 问答               Qdrant + kb-api         可重建副本，不是合同
```

人读入口：仓库根 [`INDEX.md`](../INDEX.md)。机器路由：根 [`llm-manifest.json`](../llm-manifest.json)；产品扫描另走 [`prd/llm-manifest.json`](../prd/llm-manifest.json)。

## 工作流程 · 权威分层（现在怎么读）

| 文件 | 角色 | 不是什么 |
|---|---|---|
| `prd/design/<功能>/PRD.md` | 改规则只改这里 | 不是默认切块源 |
| `prd/CONFIRMED.md` | RQ-01～RQ-21 拍板账本 | 不是功能说明书 |
| `prd/design/<功能>/brief/current.md` | 「现在怎么规定」+ chunk 契约 | 冲突时不能压过 `PRD.md` |
| `prd/VERSIONS.md` | 版本三态 | 不是功能正文 |
| `history/`、`PRD.stacked-2026-09-16.md` | 回退 / 对原文 | 不默认读、不进向量 |
| `workspace/v*` | 未升格稿 | 不能覆盖 V1.4.0 |
| `site/docs/design/` | 本仓库 H5 / 问答的需求与 STEP | 不是 Hayyo App 规则 |
| 本夹 `knowledge/` | 方法与讲解 | 不是合同、不进向量 |

**版本三态**必须分开，否则「磁盘上最新的 Word」会被当成线上规则：

1. **已收录**：写进功能 `PRD.md`，能当现行（当前到 V1.4.0）
2. **待确认收录**：人还没点头，即使文件里出现了也不能覆盖
3. **工作区文档，非权威**：只在 `workspace/<版本>/`（V1.5.0 是这个状态）

**产品 vs 工程**：钱包 / 房间规则在 `prd/`；本机知识问答、Docker、第四 Tab 在 `site/docs/design/`。问答日志页不是运营后台，禁止写进 `prd/design/admin/`。

后台独立成模块：配置字段只写在 `admin/PRD.md`，客户端用「关联后台」指针，不复制同一条公式。

## 工作流程 · Word 洗成权威 PRD

8 月 21 日定主方案：把 Word **洗成 Markdown 文档知识库**，当时明确 **不是 RAG、不是另写一套知识库软件**。向量问答是一个月后才加的第三层，语料用的是 brief，不是当初那份叠稿。

### 原文长什么样

`Aold_D/`（旧称 `demo/`）是 **按发版切的 Word 增量包**，不是按功能沉淀的知识库：

- V1.0.0 是基线全集（封面还写 Samer）
- 后面多数版本只写「这版改了什么」，不整本重抄
- 另有独立后台 Word、门票 Excel、补丁包
- **章节号不能当功能 ID**：各版都从 `3.1` 起编，V1.0.0 的 3.1 是登录，V1.1.0 的 3.1 可能是 YallaPay

因此不能「按版本文件夹继续堆」，也不能「默认只渲染最后一个 `### V1.4.0`」——会把签到这种从未在 1.4.0 重写的基线藏掉，也会把拉新 1.4.0 增量误当成全貌。

### 抽取（保真，不发明需求）

1. 用 Python 打开 docx（zip），读 `word/document.xml`
2. 按段落样式抽标题，按表格抽「功能名称 / 字段描述 / 需求描述」
3. 从 `word/media/` 抽图，放到该功能 `images/`，文件名带版本，例如 `v1.0.0-auth-login-002.png`
4. `PRD.md` 用相对路径 `![](images/...)` 挂在对应规则旁
5. 每个来源版本另存 `history/V1.x.x.md`，接近原文切片，供对账
6. Word 原件留在 `Aold_D/`，不删

约束：

- **文字 + 原图一起构成权威**。大量规则靠「图1」说清。
- **禁止看图 OCR 出另一套文字去压过原文**。图文冲突标 `needs-review`，链回原节。
- 原文没写的接口、状态机、验收 **不编**，标 `needs-input`。
- 图按功能拆开；H5 不预加载全部图片。

### 按项目功能切目录

不是按 Word 目录号，而是按项目功能（25 个，含独立 `admin`）：

- 同一主题以后出现的已收录版本为准
- 补丁包里的能力按功能收录，不因「补丁」降级
- 跨模块残段进 `infra`
- 爆奖礼物：客户端进 `room`，后台进 `admin#admin-gift-burst`
- 积分提现独立成 `payout`，不并进 `yallapay`

每个功能目录：

```text
prd/design/auth-login/
  PRD.md
  changelog.md          版本级摘要，不是段落 diff
  brief/current.md      后来才有的派生层
  history/
  images/
```

### 新版本怎么入库（以 V1.4.0 为例）

1. 先抽目录，区分新能力 / 既有功能补齐 / 明确不入库
2. 版本外后台 **不绑客户端发版**，不要当成 App V2.0.0，也不和已入库 Samer 后台 v2.0.0 混版
3. 封面写 v1.4.1 的拉新文档，切片仍挂 V1.4.0
4. 主动排除项写在 [`prd/VERSIONS.md`](../prd/VERSIONS.md)
5. 写入对应功能 `PRD.md`（清洗前叠在文后；清洗后并入现行正文）

「最新」= **已收录主线截止后仍有效的全部规则**，不是「只显示 V1.4.0 那一节」，也不是磁盘上日期最新的 Word。

## 工作流程 · 叠稿洗成现行正文（方案 B）

第一版权威 `PRD.md` 为了保真，实际是 **各版 Word 表按旧→新整段叠进同一文件**，文首写「后文覆盖同主题前文」。能溯源，但打开登录注册会先看到 V1.0.0 旧句；单元格大量 `<br>`；`admin` 一度四千多行新旧混检。

9 月 15～16 日对 25 份 `PRD.md` 做内部核定（**没有**对照 Hayyo 业务代码，RQ-20 延期）。用 `req-confirm` 做成 RQ-01～RQ-21，写入 [`prd/CONFIRMED.md`](../prd/CONFIRMED.md)。这类冲突必须人拍板，例如：拉新 V1.4.0 删了「审核中 / 待领取」，文首又说领取校验不重写。

方案 B 具体做：

1. 叠稿整份快照进 `history/PRD.stacked-2026-09-16.md`
2. 现行 `PRD.md` 去掉 `### V*` 叠写，只留截至 V1.4.0 仍有效的规则
3. 主体仍是 Word 那套表，这一步 **没有** 改成说明书体
4. `CONFIRMED.md` 后来定为拍板账本：日常改功能直接打开 `PRD.md`，冲突再对账
5. `history/`、`Aold_D/`、`workspace/v1.5.0` 不改、不升格

清洗后 H5 文档索引地址不用改，Docker 也不用为这次清洗重启。清洗 **没有** 解决「人打开还是 Word 表」，所以必须再做 brief。

## 工作流程 · brief 与切块

H5 知识库 PRD 定过：H5 不另起权威、不把 PRD 拆成可独立维护的 JSON 知识条。brief 能并存的前提是写明 **派生、非权威**；和原文冲突时改 brief，不改原文迁就说明。

同一份 `brief/current.md` 干两件事：给人读现行；给后面按 `###` 切块。不是两套稿。

### 路径与站点

- 路径：`prd/design/<功能>/brief/current.md`
- 侧栏点功能：默认仍打开 `PRD.md`
- 阅读器顶栏同一排：`查看旧版逻辑 | 变更记录 | 发版说明 | 查看关系 | PRD | 功能描述`
- INDEX / VERSIONS 不加这两个按钮；admin 后来也有 brief，切块走同名锚

### 固定骨架（禁止改名、禁止调序）

切块脚本只认标题和 HTML 注释：

```text
# {功能名} · 现行说明
## 元信息          chunk:no
## 范围            chunk:default
## 总流程          chunk:default（可含 mermaid）
## 业务逻辑        每个 ### 一块  section=logic
## 客户端页面      每个 ### 一块  section=page
## 后台影响        通常 1 块      section=admin
## 关联影响        每对方功能 1 块 chunk:related-row（默认不进向量）
## 相对变化        chunk:changelog（默认不进）
## 原文 / 计划预览 / 待校对     chunk:no
```

注释形态：

```html
<!-- chunk:default section=logic id=auth-login.logic-sms -->
<!-- chunk:related-row section=related id=auth-login.related-payout target=payout -->
<!-- chunk:no -->
```

工作区 V1.5.0 只许出现在「计划预览」，不进现行节。

### 怎么洗每一份 brief

原料是现行 `PRD.md` + `CONFIRMED.md`，不再从合订本判断覆盖：

1. 按主题拆成逻辑点 / 页面点，不要整篇散文
2. 被覆盖的旧句不再当现行写；未改过的 1.0.0 基线写进对应主题
3. 后台字段不复制，只指针
4. 节内自包含：禁止「如上 / 同个人页」离开上下文断义
5. 冲突、原文残句进「待校对」，不擅自选边
6. frontmatter：`authority: derived`，`cutoff: V1.4.0`，`status: pending-review`

量级：客户端 brief 的 `chunk:default` 从约 5 块（`room-list`）到约 21 块（`referral`）；`admin` 按页面锚点约 103 块。与索引对账约 **346** 块。

### 入库切哪些

| 切 | 不切 |
|---|---|
| `brief/current.md` 的 `chunk:default` | `PRD.md` |
| admin → collection `hayyo-admin` | `history/`、`archive/`、`Aold_D/` |
| 其余 → `hayyo-client` | `chunk:related-row`、`chunk:no`、changelog |
| 相关功能靠二次跳转 | YAML、H1、元信息、计划预览、待校对 |
| | 超长块禁止二次切分，超限不入库 |

每条 payload 带：`feature_id`、`cutoff`、`authority=derived`、`section`、`heading`、`anchor`、`path`、`chunk_id`（如 `vip.logic-pretty`）。

出处定位用 `{#锚点}` 或标题；**chunk 注释不能当 DOM id**。

改 `PRD.md` 后要重做 brief（覆盖 / 增量需人确认一次）；brief 变了必须 **重建索引**。人看 diff 用 git，不把 brief 全文灌进 MySQL。

## 工作流程 · H5 文档索引（L1 / L2）

8 月 24～26 日把「要不要在 H5 上做知识库」收成 L1 / L2 / L3，**当时只做 L1+L2**，向量问答另立项。这是后来接第四 Tab 的地基。

仍有效的决定：

- H5 只是阅读器 / 检索层，不成为第二套正文
- 不重切功能目录，不拆 JSON 知识条
- 第三视图现称「文档索引」（避免和问答混名）
- 从图打开文档：切到阅读器，保留图上选中；后台节点落到 `admin` 锚点
- L2 索引不入库：浏览器 `fetch` Markdown，内存建索引，最多 20 条
- 不按 `### V*` 只显示最后一节
- 文首「更新」日是入库日，不是功能上线日
- 必须本地 HTTP，静态根是 **仓库根**（要读 `/prd/`）
- 无账号、不做 CMS、不在线编辑、不让检索结果改写 PRD
- 渲染 Markdown 时禁止执行文档内脚本

站点在 `site/`，URL 仍是 `/feature-interaction/`。Docker 静态卷挂仓库根只读，不是只挂 `site/`。

## 工作流程 · 知识问答

这是 **工程 PRD**，不进 `prd/design/`。需求在 [`site/docs/design/kb-qa/PRD-知识问答-v3.md`](../site/docs/design/kb-qa/PRD-知识问答-v3.md)。复制 / 赞 / 踩 / 刷新 / 对话区样式是独立专题 [`kb-qa-feedback`](../site/docs/design/kb-qa-feedback/INDEX.md)，**不把增量写回 v3**。

开发节奏：审查 PRD → 拆 STEP → 复审验证版 → 四里程碑计划 → 再写代码。里程碑按可演示能力切（能进壳 / 能建索引 / 能问答 / 能看日志），不按前后端分层，也不一次做完全部 STEP。

### 运行

`site/docker-compose.yml`：nginx `127.0.0.1:18765`、Qdrant、MySQL（只存轮次日志）、kb-api。密钥只在 `site/.env`。只绑本机，不当公网站点。从仓库根启动要用 `-f site/docker-compose.yml`，Compose 读的是启动目录下的 `.env`。

### 一轮怎么走

不是一个模型既改写又检索又回答。链路见 [`讲解-检索链路.md`](讲解-检索链路.md)。K / n 见 [`讲解-K与n与TopP.md`](讲解-K与n与TopP.md)。跨功能问句见 [`案例-跨功能与单功能.md`](案例-跨功能与单功能.md)。

硬规则摘要：

- 多意图 = 点名了几个已有功能 ID，不是一句话有几个问号
- 改写失败：整轮失败，不降级成用原句检索
- 换题不带上一轮 chunk
- 生成不得使用未进本轮 Top n 的数字 / 字段
- 互斥块并列，不选边
- 交叉条件 brief 没写：禁止多份相乘
- 出处用 `chunk_id`，不要用 `[1]` 这种阿拉伯数字序号

口语对不上功能 ID 时靠 [`site/kb-api/feature_aliases.json`](../site/kb-api/feature_aliases.json)，改写禁止发明仓库里没有的 ID。

## 经验 · 可复用做法

### 经验 · 先有一份合同，再派生长层

权威、派生、向量必须三套身份。问答层当合同，改需求就会改错文件；从叠稿 `PRD.md` 直接切块，会把废规则检索出来。

### 经验 · 增量 Word 要按功能合并，不要按版本堆

查登录不能只看最后一版；查休闲游戏又几乎不在 V1.0.0。功能一份当前正文，版本只记 changelog 和 history。

### 经验 · 给人读的骨架 = 切块契约

不要事后对散文乱切。固定 `##` / `###` / 锚点 / `<!-- chunk:* -->`，脚本只认注释。关联一行一个对方功能，避免整张表进一条向量。

### 经验 · 工程文档和产品规则分夹

H5、问答、Docker、本夹知识都不是 Hayyo 产品规则。日志 / 热度是本站点工程页，不写入 `prd/design/admin/`。

### 经验 · 先方案后落盘，覆盖要人点一次

文档、代码、Word 都是确认才写。brief 的覆盖 / 增量不能让模型自己悄悄判断「只是改皮」。拉新 V1.4.0 看起来像改皮，但「可不按顺序领」、H5 落地已经改规则。

### 经验 · 增量 UI 另开专题，不修订主 PRD 成 v4

反馈与对话样式覆盖了 v3「正式空状态不做 chips」等条款。改那些读 feedback 夹；检索公式仍以现网 / v3 为准（以专题自己写的边界为准）。

## 教训 · 踩过的坑

### 教训 · 增量 Word 不是现行全貌

只看最后一节会丢基线、会把补丁当成全集。封面版本号、文件日期、章节号都不能当权威。

### 教训 · 「后文覆盖」若旧句仍留在文前，等于没覆盖

叠稿只适合归档，不适合当默认阅读和默认切块。方案 B 是在修这个，不是推翻按功能切目录。

### 教训 · brief 未校对就进了向量

事实：各功能 `brief/current.md` 的 `status` 仍是 `pending-review`；问答已按 `chunk:default` 切块上现网（约 346 块）。

语料没有人工校对，答案只能当「派生稿检索结果」，强度要打折。对不上时打开对应 `PRD.md` 校对，不要把问答当合同。这是已知债，不是已经验证过的语料质量。

### 教训 · 出处不要用阿拉伯数字编号

多问 + 出处写成 `[1]` + 问句里带数字时，模型会把问句里的数字或出处序号当成规则。出处写 `chunk_id`（如 `vip.logic-pretty`）。

### 教训 · 同一块里两套「级 / 档」会串台

例如 VIP1–VIP11 与靓号「共十级」。切块应尽量拆开；生成侧也必须自己区分。单靠重排或 Top-P 躲不开。

### 教训 · 漏点名发生在口语 ≠ 功能 ID 时

「代理转账」要对上 `merchant`。靠别名表，不靠发明 `vip-level` 这种 ID。同一功能里的两问仍是一个 ID，走单路。

### 教训 · 交叉未写不能乘出来

「等级 2 且 VIP5 能否用拉新」：三份 brief 都没有这道组合门槛。分路保证每本说明书都翻到，不保证三本相乘有结论。

### 教训 · 启动目录和 .env 不一致会假配 Key

从哪执行 `docker compose`，就读哪的 `.env`。Key 示例在 `site/.env.example`。

### 教训 · 工程 PRD 的实现状态会过期

v3 文首仍写「未实施」（本轮按确认 **不改** v3）。讲解稿曾写「kb-api 尚未落地」，与 9/17 现网不符，搬家时已改讲解稿这一句。以后改现网，记得改对应讲解，或接受 PRD 文首滞后。

### 教训 · H5 / 问答 / 后台皮 都不是产品规则

第二套正文一旦可独立维护，立刻和「一份当前权威」冲突。
