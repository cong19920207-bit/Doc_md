## 3. 行为约定

- 同一会话同一时刻只有一个普通发送或刷新在执行；顺序为 `insert_running` → 校验归属 → 查重 → 抢占 → 写 User。被拒请求也留执行记录（`error_type` 为拒绝原因，`used_knowledge_rag=0`）。
- 执行权在 `finish` 落定终态后释放；客户端断开导致生成器关闭时，外层按本执行条件释放。每进入新阶段续期。
- 新版本「保存成功且结果为 success/refuse/empty」才被采用；error_notice、partial、保存失败均不替换原默认版本。L1 只取当前版本，每轮 `exec_id` 取自该 Assistant 行。
- 补写：首写失败后先存承载，再同步补写 2 次（间隔 0.5 秒、1 秒）；仍失败则写阻塞（写库失败时记进程内），`msg_save=failed`。补写与重试保存只更新 `msg_save`、`assistant_msg_id`、`pending_reply`，不改业务结果与执行状态。
- 热度：`schema_ver≥2` 只统计 `used_knowledge_rag=1`；旧记录按旧口径计入并单列。
- 前端：丢弃 `exec_id` 与当前目标不一致的 SSE 事件；忙碌/阻塞撤掉本地这一对消息、原文放回输入框；刷新失败恢复原版本；「‹ n/m ›」只切换查看；赞踩发往当前查看版本的执行；未保存回复不显示赞踩、显示「重试保存」。

## 4. 未验证与过渡

- AT-34 只在数据层验证（刷新沿用原 `time_base`）；按时间基准解释「昨天」等在 Q12/Q17 接入。
- 「通过交付检查」在 Q19 前按旧 `status` 判断。
- 进程内阻塞备份与承载备份在服务重启后丢失；此时重试保存返回 `save_source_lost` 并解除阻塞。
- 前端版本列表是本地展示缓存；换设备只看到服务端当前采用版本（`payload.messages` 仍为展示缓存，改读 `/messages` 留在后续 STEP）。
- 断线场景下执行仍按 M1 行为在检测到断开时以 `interrupted` 收尾；「断线继续」属 Q10（M5）。
