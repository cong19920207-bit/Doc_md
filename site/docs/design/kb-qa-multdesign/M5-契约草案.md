## 1. Q11 Router v3

### Router 输出 Schema

| 字段 | 类型 | 规则 |
|---|---|---|
| `route` | 字符串 | 只认六类：`knowledge_query`、`conversation_task`、`ack`、`smalltalk`、`out_of_scope`、`unclear`；大小写不同、`context_dependent` 均非法 |
| `requires_history` | JSON 布尔 | `"true"`、0/1 非法 |
| `confidence` | 数值 0～1 | 布尔、字符串、NaN、越界非法；低置信度只记录，不改分支（G-E03 兜底 M5 不启用） |
| `reason` | 非空字符串 | 只记日志，代码不解析 |

多余字段不使用，只记字段名（`extra_keys`）。输出可带代码块包裹，取第一个 JSON 对象。

### 错误

| code | 条件 | 处理 |
|---|---|---|
| `router_invalid` | 任一字段非法、非 JSON | 执行异常；不当 `unclear`，不检索、不生成；`error_notice` 落库；Runtime `router.raw` 存截断原文 |
| `router_fail` | 调用失败、空响应 | 同上；不重试（G-E02 未定） |
| `missing_key` | 未配置 DeepSeek Key | 同上，提示缺 Key |

### Runtime（`qa_rounds`）

- 新列：`route VARCHAR(24) NULL`、`requires_history TINYINT NULL`、`router JSON NULL`。
- `router` 结构：`{confidence, reason, valid, error, detail?, extra_keys, prompt_ver: "router-v3", raw?}`。
- 每次执行只在 Router 这一步写一次，后续步骤不改写；刷新是新执行，按原快照 L1 单独分类。

### SSE

- 新增 `stage` 值 `route`（前端「理解问题中…」）。

## 2. Q12 非知识分支

### 分支行为

| route | 回复来源 | 后续模型 | Knowledge / Memory | `biz_result` |
|---|---|---|---|---|
| `ack` | `ACK_REPLY_POOL` 随机一句 | 无 | 不调用 | `not_applicable` |
| `out_of_scope` | `OUT_OF_SCOPE_REPLY_POOL` 随机一句 | 无 | 不调用 | `refused` |
| `smalltalk` | Smalltalk Prompt（L1 + 当前输入） | 1 次 | 不调用 | `not_applicable` |
| `unclear` | Clarification Generator Prompt v2 | 1 次 | 不调用 | `clarify` |
| `knowledge_query`、`conversation_task` | 原知识链路（`conversation_task` 分支执行随 Q13/M6） | — | — | 原映射 |

- 两个话术池独立，取值为 PRD 配置示例，写在 `settings.py`；后台管理随 A09。
- 旧 `status` 仍写 `success`，`done` 事件结构不变（`c_gen: []`、`refused: false`）；`used_knowledge_rag=false`，不进热度。
- 回复照常写成 Assistant 消息（`completeness=complete`），可刷新、可赞踩。

### 依赖检查

- 非知识分支不检查 Key 与知识索引，也不 ping Qdrant；知识分支在 Router 之后才做原有检查（`missing_key` / `index_not_ready`），规则不变。

### 澄清输出 Schema

- 合法 JSON，唯一字段 `clarification`，值为非空字符串；多余字段、空值、非 JSON 均为 `clarify_invalid`。
- 输入：L1、已恢复的必要历史（Q12 固定为「（无）」）、停止原因 `router_unclear`、本轮提问时间（UTC，时区换算待 G-E08）、当前原句。

### 错误

| code | 条件 | 处理 |
|---|---|---|
| `smalltalk_fail` | 闲聊模型调用失败或空回复 | 执行异常，提示「回复生成失败，可重试。」，`error_notice` 落库 |
| `clarify_fail` | 澄清模型调用失败或空回复 | 执行异常，提示不写成反问；`error_notice` 落库 |
| `clarify_invalid` | 澄清输出不合 Schema | 同上 |
| `reply_pool_empty` | 话术池为空 | 执行异常，不返回空回复 |
| `missing_key` | 闲聊/澄清缺 Key | 同上 |

- 闲聊、澄清失败时追加诊断事件 `model_error`，`code` 为 `smalltalk:<code>` / `unclear:<code>`（G-E06-6 记录点）。

### SSE

- 新增 `stage` 值 `smalltalk`（「回复中…」）、`clarify`（「整理澄清问题…」）。

## 3. Q13 任务准备、部分交付、混合越界、跨轮承接

> 门定稿：`steps-verified.md`「阻断与来源变化」2026-09-29 Q13 门冻结行（G-E01 任务/缺口部分 ①～⑥）。

### 任务准备输出 Schema（`task-prep-v1`）

| 字段 | 规则 |
|---|---|
| `tasks[]` | 最多 6 个；`task_id` 形如 `T1` 且唯一；`goal` 非空；`mode` ∈ 查询/解释/对照/整理/核验/回看/重述；`check` ∈ `ready`/`needs_history`/`needs_user_input`/`ambiguous`/`blocked_by_dependency`/`out_of_scope`；`scope`、`constraints[]`、`depends_on[]`、`gap_ids[]` 可缺省为空；依赖须指向已有任务、不得指向自身或成环 |
| `excluded[]` | `{text, reason}`，均非空；越界部分不作为任务执行 |
| `information_gaps[]` | `gap_id` 形如 `G1` 且唯一；`task_ids` 须指向已有任务；`type` ∈ `history_object`/`user_condition`/`candidate_choice`；`required` JSON 布尔；`status` ∈ `open`/`resolved`/`unresolvable`；`candidates[]`、`clue` 可空 |
| `response_constraint` | 字符串，可空 |

- `tasks` 与 `excluded` 不能同时为空。多余顶层字段不使用，只记名。
- `check` 完整枚举 8 类，其中 `knowledge_insufficient`、`error` 只由执行阶段写入，任务准备给出即非法。

### 服务端复核与出口

- 依赖未就绪的 `ready` 任务改为 `blocked_by_dependency`（逐层传递）。
- 出口：有 `ready` → `run`；否则有 `needs_user_input`/`ambiguous` → `clarify`；否则有非越界任务 → `unfinished`；否则 → `refused`。
- `run`：就绪任务合并跑一次知识链路；任务说明（执行/未完成/不执行、回答约束）经本请求 `cfg["_task_brief"]` 进 Rewrite 与 Generate 消息。有未完成或不执行项时 `partial=true`，成功结果记 `biz_result=partial`。
- `clarify`：Clarification Generator 收到「尚未解决的信息点」与候选、承接线索作为已恢复历史，停止原因 `task_needs_user_input` / `task_ambiguous`；`biz_result=clarify`；不检索。
- `unfinished`：不调模型，逐项说明原因；`biz_result=insufficient`。缺较早历史的原因固定为「需要更早的对话内容，当前暂不支持查找」（M6 前）。
- `refused`：越界话术池；`biz_result=refused`。
- 非 `run` 出口不检查 Key 与知识索引，不 ping Qdrant。

### 跨轮承接

- 取清空边界之后、本问（刷新时为原问题）之前最近一个逻辑回合的当前版本回答；其执行 `biz_result` 为 `clarify` 或 `partial` 才承接。不受 L1 窗口限制。
- 承接线索内容：上一轮结果、原任务原句、上一轮回复（截 1000 字）、未完成项（原因与候选）、已交付项（不要重做）、已标越界项（不自动执行）；Router unclear 的澄清没有任务集时只含前三项。
- 同时交给 Router（`carry`）与任务准备；读取失败按无承接处理。

### Runtime（`qa_rounds`）

- 新列 `task_prep JSON NULL`，每次执行写一次：成功为 `{ver, carry{from_exec_id, from_logical_round_id}|null, valid:true, error:null, tasks[+reason], excluded, information_gaps, response_constraint, outcome, partial, extra_keys}`；失败为 `{ver, carry, valid:false, error, detail, raw?}`。

### 错误

| code | 条件 | 处理 |
|---|---|---|
| `task_prep_invalid` | 输出不合 Schema | 执行异常；不降级为单任务、不检索、不重试；`error_notice` 落库；诊断 `model_error`（`task_prep:<code>`） |
| `task_prep_fail` | 调用失败、空响应 | 同上 |
| `missing_key` | 未配置 DeepSeek Key | 同上 |

### SSE

- 新增 `stage` 值 `task_prep`（「梳理任务中…」）；`done`/`error` 结构不变，未新增事件（G-E05 事件协议未冻结）。

## 4. Q17 唯一 Rewriter v3 与旧 Pipeline 适配

### 输出 Schema（`rewrite-v3`）

| 字段 | 规则 |
|---|---|
| `status` | `ready` / `needs_context` |
| `standalone_query` | ready 时非空；needs_context 时一律置空 |
| `response_constraint` | 字符串，可空 |
| `missing_context[]` | `{task_id, type, clue}`；`type` ∈ `history_object`/`user_condition`；`task_id` 须为本轮就绪任务；ready 时必须为空，needs_context 时必须非空 |

- 旧字段映射：`standalone_query` → `rewrite_query`；`named_feature_ids`、`same_topic` 原样交旧 `retrieve`/`rerank`/`apply_floor`。
- 多余字段不采信（例如附带的「知识库没有该规则」），只记名 `extra_keys`。
- 任一处非法：`rewrite_fail`，Runtime `rewrite = {valid:false, detail, raw(截断), prompt_ver}`，诊断 `model_error`（`rewrite:invalid`）。
- Prompt `REWRITE_V3_PROMPT` 写在代码里；`/config` 的 `rewrite_prompt` 照存不用。旧 `parse_rewrite` 保留给旧用例。

### needs_context

- 本轮不检索、不重跑 Router、不再次改写。
- 缺用户条件（`user_condition`）→ Clarification Generator，停止原因 `rewrite_needs_context`，`biz_result=clarify`。
- 只缺较早历史 → 不调模型，逐项说明「需要更早的对话内容，当前暂不支持查找（缺：…）」；同轮其他问题说明本轮未执行；`biz_result=missing_context`。

### Runtime（`qa_rounds`）

- 新列 `rewrite JSON NULL`：`{valid, status, response_constraint, missing_context, confidence, extra_keys, prompt_ver}`。
- 新列 `call_usage JSON NULL`：本执行各模型调用次数 `{router, task_prep, rewrite, smalltalk, clarify, generate, check, repair}`，终态时写入，后端维护、任何分支不归零。

## 5. Q18 Generate 实际输入交接

### 交接内容（经 `cfg["_handoff"]` 进入 `generate_messages`）

- 原句、独立问句、任务说明（Q13）、Rewriter 回答约束、本轮提问时间（`KB_DISPLAY_TZ`，默认 Asia/Shanghai）、知识版本说明（只有当前版 brief、不含历史版本）、交接规则（历史不是证据、新证据推翻旧结论先更正、片段只能按片段引用、冲突并列不裁决）。
- 相关历史对话：requires_history、要求不重复（约束里含「不/别/避免/勿…重复」）或存在「核验」任务时，给出 L1 全部完整回合原文。
- 核验目标：存在「核验」任务时为 L1 最近一条回答原文。
- 每个知识块带 `content_hash`（仅当对应本次正文）；只剩片段时标「正文范围：片段（非全文）」。

### 合同校验

- 要求不重复却没有此前回答，或核验却没有目标回答 → `generate_contract_fail`，执行失败，不检索、不生成。

### 来源身份

- `fill_block_content`：从入库元数据回填正文时同时换成入库 `content_hash`，`content_scope=full`；只剩 excerpt 时 `content_scope=excerpt`、`content_hash` 清空。公开卡片（`c_gen`）增加 `content_scope`，仍不含正文。

### 业务结果

- `biz_result` 枚举增加 `conflict`、`missing_context`。
- 点名 ≥2 个功能而部分功能无块 → `partial`；重排 0 块 → 原拒答（`insufficient`）；冲突由 Q19 检查输出。

### 引用复核接口

- `GET /api/kb/chunk?path=&chunk_id=&content_hash=`，权限「知识问答」。
- 200 `{ok, path, chunk_id, heading, anchor, feature_id, content_hash, content}`；hash 不符 409 `source_changed`（不含正文）；读不到 404 `source_not_found`；缺参数 400 `invalid_request`；读取异常 503 `source_unavailable`。
- 前端点引用先调此接口，失败时提示、不打开文档。

## 6. Q19 Evidence check 与最多一次修正

### 检查输出 Schema（`check-v1`）

- `{check_status: pass|fail, issues[{answer_span, evidence_ids, reason}], conflict: bool}`。
- pass ⇔ issues 为空；`evidence_ids` 只能是本轮 `E1…En`；`answer_span` 非空时必须出自被检查草稿；`reason` 非空；最多 12 条。
- 空响应、调用失败 → `check_fail`；其余不合 Schema → `check_invalid`；修正调用失败或空 → `repair_fail`。均为执行异常，不放行、不重试。

### 流程

- 生成完成后用同一份 c_gen 检查；块外数字（旧数字规则）自动追加一条问题并判 fail。
- 首检 fail、未修正、执行总截止剩余 ≥120 秒 → 修正 1 次（`repair_count=1`）→ 复查新草稿；复查 fail 不再修正。
- 执行总截止 = 接受时刻 + 300 秒（与执行权租期同值，续租不延长）。
- 通过：保存通过检查的那份正文，`check_status=pass`；原文互相冲突 → `biz_result=conflict`。
- 未通过：只保存失败说明（「该问题未能形成可靠回答…」），旧 `status=empty`、`biz_result=insufficient`、`check_status=fail`，不替换原有效版本。
- 异常：保存 `error_notice`「证据检查失败，本轮回答未交付。可重试。」，`check_status=error`，执行失败。
- 非知识分支、澄清/说明出口不检查，`check_status=not_run`。
- `post_check_answer` 不再改正文，块外数字只返回 `numbers_ok=false`。

### Runtime

- 新列 `evidence_check JSON NULL`：`{ver, evidence[{evidence_id, path, chunk_id, content_hash, content_scope}], rounds[{draft_hash, check_status, issues, conflict}], repair_count, budget_stop?, error?, final_hash}`；不存草稿全文与证据正文。

### SSE

- 新增 `stage` 值 `check`（「核对原文中…」）、`repair`（「按原文修正中…」）。
- 新增事件 `check {check_status: pass|fail|error, replaced, text, round_id}`：`replaced=false` 表示草稿即正式；`true` 时 `text` 为修正稿或失败说明。

## 7. Q10 断线继续、统一终态、SSE 与草稿展示

### 执行与订阅

- `POST /api/kb/ask` 受理后执行在服务端后台任务中运行，SSE 只是订阅；客户端断开不取消执行。
- 执行总截止 300 秒：超时即取消进行中的调用，写 `exec_state=failed`、`error_type=exec_timeout`，保存超时说明（`error_notice`），推送 `error{type: exec_timeout}`；之后晚到的结果不改写终态。

### 状态接口

- `GET /api/kb/rounds/{exec_id}/status`，权限「知识问答」，只返回本人执行；不存在/非本人/会话不可见统一 404 `round_not_found`。
- 返回 `{ok, exec_id, conversation_id, logical_round_id, op_type, terminal, derived, status, statuses(六类), error_type, text, completeness, assistant_msg_id, version_no, adopted, save_blocked, c_gen}`。
- 未终态时：本进程在跑或会话执行权仍属于它 → 运行中；否则按中断报告（`derived=true`、`error_type=service_interrupted`），只读、不写库。
- `GET /api/kb/rounds/{id}` 等明细接口仍要「问答明细」。

### 前端

- 流式 token 期间标「草稿·核对中」；`check` 事件通过转正式，替换时显示修正稿（标「已按原文修正」）或失败说明。
- 读完 SSE 没有 `done`/`error`，或连接中途异常 → 每 1.5 秒轮询状态接口，最多约 6 分钟；404 按提问失败处理，超时提示稍后重开会话查看；不重发 ask。
- 旧 `done.status=interrupted` 的处理保留（服务端已不再产生）。
